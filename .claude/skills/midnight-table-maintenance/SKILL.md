# 심야 테이블 유지보수 절차

사용자는 **코드를 보지 않고 채팅 보고만으로 판단한다.** 서버에 접속하거나 배포에 손대지 않는다.
따라서 원인 파악·수정·검증·배포·보고를 전부 이쪽에서 책임진다.

저장소: 작업 공간의 `midnight-table/` (사용자 PC 사본은 바탕화면 `online` 폴더)

## 0. 지켜야 할 원칙

- **우선순위 순서를 어기지 않는다**: ① 재미와 촉감 ② 구조의 정확성과 안정적인 실시간 동기화 ③ 장르 고유의 판단과 보상 설계 ④ 완성도 ⑤ 시나리오 개수
- **쉬운 수준에 스스로 상한을 두지 않는다.** 요청은 출발점이다. 장식이나 기능 개수로 품질을 대신하지 않는다.
- **구현 → 실제 실행 → 관찰 → 디버깅 → 개선 → 재검증을 스스로 반복한다.** 한 번 고쳐서 동작하는 것처럼 보인다고 바로 완료 보고하지 않는다. 새 기능도 "일단 동작하는" 수준에서 멈추지 않는다.
- **핵심 설계 결정과 충돌하면 조용히 바꾸지 않는다.** `PROJECT.md`의 설계 결정표와 어긋나는 요청이면, 원래 설계와 다르다는 점을 먼저 알리고 확인받은 뒤 진행한다.

## 1. 절차

### ① 현황 파악
`PROJECT.md`를 먼저 읽는다. 그다음 `ISSUES.md`에서 관련 항목이 이미 있는지 본다.

### ② 이슈 기록
사용자의 말("여기 이상해", "이것 좀 넣어줘")을 **증상 / 재현 방법(추정 포함) / 기대 동작**으로 구조화해 `ISSUES.md` 열림 목록에 적는다. 기록하고 나서 고친다.

### ③ 원인 파악
증상이 아니라 원인을 찾는다. 재현부터 한다 — 서버를 띄우고 브라우저를 열어 직접 본다.
구역 격리 관련이면 **반드시 3명 이상**으로 확인한다(2명으로는 증명되지 않는다).

### ④ 판단 경계선 — 물을지 말지
- **스스로 결정**: 구현 방식, 파일 구조, 변수명처럼 정답이 없고 사용자 경험에 영향이 적은 것
- **먼저 묻기**: 게임 룰, UX, 우선순위처럼 취향과 판단이 필요한 것 → 옵션과 장단점을 짧게 정리해 채팅으로
- **반드시 묻기**: 비용이 발생하거나 되돌리기 어려운 결정은 사소해 보여도
- 애매하면 "이 정도는 물어볼 가치가 있는가"로 판단하되, 사소한 질문을 남발하지 않는다

### ⑤ 수정
당장 동작하게만 땜질하지 않는다. 필요하면 리팩터링을 병행해 코드 품질이 나빠지지 않게 한다.

### ⑥ 회귀 테스트 — 전체
```bash
npm test
```
관련 항목만이 아니라 **전체**를 돌린다. 통과 못 하면 배포하지 않고 원인부터 해결한다.
**새 기능을 추가했으면 그 기능의 검사도 `TESTING.md`와 테스트 스크립트에 함께 추가한다.**
버그를 고쳤으면 그 버그를 잡아내는 검사를 추가한다.

### ⑦ 민감정보 점검
API 키·비밀번호가 코드나 커밋에 들어가지 않았는지 확인한다. 전부 `.env`(gitignore)와 환경변수로만.
클라이언트 번들에 키가 섞이지 않았는지도 본다 — 브라우저로 나가는 것은 전부 공개된 것으로 취급한다.

### ⑧ 커밋
의미 단위로 나누고, 커밋 메시지에 **무엇을 왜 바꿨는지** 남긴다.

### ⑨ 배포
- 배포 전 `npm run backup` 실행
- 회귀 테스트를 통과하지 못하면 배포하지 않는다
- **배포 직전, 검증 전용 서브에이전트를 한 번 띄워 회귀 테스트 결과를 독립적인 시각으로 재확인한다.** 이 외에는 여러 에이전트를 병렬로 굴리지 않는다 — 이 규모에서는 한 세션이 `PROJECT.md` 하나를 일관되게 참고하는 편이 안정적이다
- 안정적으로 동작이 확인되면 git 태그(`v2`, `v3` …)를 찍어 되돌아갈 지점을 남긴다
- 배포 후 심각한 문제가 생겼는데 원인을 바로 못 찾으면, **먼저 직전 안정 태그로 되돌리고 그 사실을 보고한 뒤** 원인 분석을 이어간다

### ⑩ 계정·키가 필요할 때
호스팅 가입, API 키 발급처럼 사용자만 할 수 있는 단계를 만나면 **임의로 건너뛰거나 우회하지 않는다.**
멈추고 — 어느 서비스에서 / 무엇을 / 어떻게 전달하면 되는지 구체적으로 안내하고 — 받은 정보로 이어간다.
비용이 발생할 수 있으면 예상 비용과 이유를 먼저 알리고 확인받는다. 무료 티어를 우선 검토한다.

### ⑪ 보고 — 항상 같은 형식
```
무엇이 문제였나 / 무엇을 요청받았나
어떻게 해결했나
회귀 테스트 결과
남은 리스크 · 트레이드오프
```
장황한 기술 설명 대신 **사용자가 판단하는 데 필요한 정보** 위주로 간결하게.

### ⑫ 뒷정리
`ISSUES.md`에 완료 표시와 **어떻게 고쳤는지** 기록. 설계에 영향을 줬으면 `PROJECT.md` 갱신.
사용자 PC 폴더(바탕화면 `online`) 동기화.

## 2. 이 절차에 포함되지 않는 것 — 장애 감지

서버가 죽거나 심각한 오류가 나도 사용자는 모른다. 그런데 이 스킬은 **사용자가 말을 걸어야만 동작한다.**
그래서 장애 감지는 이 절차와 분리해, 요청과 무관하게 상시로 도는 **예약 작업**으로 따로 둔다
(주기적으로 `/api/health`를 확인하고 이상하면 알림). 유지보수 요청을 처리하면서 이 절차 안에서 점검하려 들지 않는다.
